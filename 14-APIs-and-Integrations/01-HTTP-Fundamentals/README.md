# 01 — HTTP Fundamentals: Idempotency

[Back to module overview](../README.md)

## Beginner: What Idempotency Actually Means

An idempotent request produces the same end result no matter how many times it's retried. This matters enormously in practice: a client that sends a request and never receives a response (a network timeout, a dropped connection) genuinely cannot tell whether the server processed it or not — its only safe option is to retry. Whether that retry is safe depends entirely on whether the request was idempotent. This lesson demonstrates the real consequence of getting this wrong, against a genuine embedded HTTP server, with real requests.

## The Violation: A Real Duplicate-Creation Bug From a Non-Idempotent Retry

```java
server.createContext("/orders", exchange -> {
    String id = String.valueOf(nextId.getAndIncrement()); // a NEW id, every single call
    orders.put(id, "pizza order");
    respond(exchange, 201, "{\"id\":\"" + id + "\"}");
});
```

A plain `POST /orders` creates a brand-new order with a new, server-assigned ID on every call — there's no way for the server to recognize "this is a retry of the same request I already handled." Verified live, simulating a client retrying the same logical request twice:

```
POST /orders -> 201 {"id":"1"}
POST /orders -> 201 {"id":"2"}
Total orders actually created: 2  <- BUG: retrying the SAME logical request created 2 SEPARATE orders!
```

A real customer, if their app retried this exact request after a timeout, would be charged for two pizzas instead of one.

## The Fix: An Idempotent Endpoint Using a Client-Supplied ID

```java
server.createContext("/orders-idempotent/", exchange -> {
    String id = ...; // supplied by the CLIENT, not generated by the server
    orders.put(id, "pizza order"); // overwrites -- same id, same result, however many times this runs
    respond(exchange, 200, "{\"id\":\"" + id + "\"}");
});
```

Verified live — the identical retry scenario now leaves exactly one order:

```
PUT /orders-idempotent/order-42 -> 200 {"id":"order-42"}
PUT /orders-idempotent/order-42 -> 200 {"id":"order-42"}
Total orders actually created: 1  <- correct: retrying the identical request left exactly ONE order
```

Because the client supplies the ID (`order-42`) rather than the server generating a new one, retrying the exact same request is a no-op the second time — `PUT`'s semantics (replace the resource at this URL with this state) make this safe by design, which is exactly why `PUT` is defined as idempotent in the HTTP specification and plain `POST` is not.

## Common Mistakes

- Assuming `POST` is always safe to retry — verified live to create a genuine duplicate when retried, precisely because plain `POST` has no built-in idempotency guarantee.
- Designing a "create" endpoint without any way for a client to supply or reference an idempotency key/ID, making safe retries structurally impossible.
- Confusing "idempotent" with "safe" (no side effects at all) — `GET` is both safe and idempotent, but `PUT`/`DELETE` are idempotent while still having real side effects (they just produce the same *end state* no matter how many times they're repeated).

## Best Practices

- Use `PUT` (with a client-supplied or otherwise stable identifier) or an explicit idempotency-key header for operations that a client might need to safely retry.
- Reserve plain `POST` for operations where duplicate submission risk is acceptable, or pair it with a real idempotency-key mechanism.
- Design any operation a client might retry after a timeout (payments, order creation) to be idempotent from the start — retrofitting idempotency after real duplicate-charge incidents is far more painful.

## Real-World Usage

Payment APIs (Stripe, for example) are the textbook real-world case: a client that doesn't receive a response after submitting a payment must be able to safely retry without risking a double charge, which is exactly why such APIs require an explicit idempotency key on payment-creation requests. The duplicate-order bug demonstrated in this lesson is a real, common category of production bug in APIs that don't account for this.

## Summary

- A non-idempotent `POST` endpoint was shown, live, to create two separate orders when a client retried the same logical request — exactly the scenario a real network timeout produces.
- An idempotent `PUT` endpoint using a client-supplied ID was shown, live, to leave exactly one order under the identical retry scenario.
- Idempotency is what makes retries — which are often the only safe option a client has after a timeout — actually safe.

## Key Terms

- **Idempotent** — a request that produces the same end result no matter how many times it's repeated.
- **Idempotency key** — a client-supplied identifier used to let a server recognize and deduplicate retried requests.
- **Safe method** — an HTTP method (like `GET`) that has no side effects at all; distinct from, though related to, idempotency.

## Interview Questions

1. **Why can't a client always tell whether its request actually succeeded, and why does this make idempotency important?**
   If a client sends a request and the connection is interrupted (a timeout, a dropped connection) before it receives a response, it genuinely cannot know whether the server processed the request before the interruption or not — the only safe way to guarantee the operation eventually happens is to retry. Whether that retry is actually safe depends entirely on idempotency: this lesson demonstrated that retrying a non-idempotent `POST /orders` request created two separate orders, verified live by the server's own order count going from 0 to 2, while retrying an idempotent `PUT` request with the same client-supplied ID correctly left exactly one order.

2. **Why does supplying the ID from the client, rather than generating it on the server, make an operation idempotent?**
   When the server generates a new ID on every request (as in the violation), it has no way to recognize that two requests represent the same logical operation — each one looks like a brand-new, distinct request. When the client supplies a stable ID (as in the fix), the server can treat the operation as "set the resource at this ID to this state," which produces the exact same end result whether it's called once or a hundred times — verified live by the order count remaining at exactly 1 after two identical `PUT` requests, compared to 2 after two `POST` requests each generating a new ID.
