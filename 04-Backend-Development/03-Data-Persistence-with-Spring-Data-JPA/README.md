# 03 — Data Persistence with Spring Data JPA

[Back to module overview](../README.md) | [Previous: Building a REST API with Spring Boot](../02-Building-a-REST-API-with-Spring-Boot/README.md)

## Beginner: From an In-Memory Map to a Real Database

Lesson 02's `TaskController` stored tasks in a plain `Map<Long, Task>` — convenient, but everything vanishes the moment the process restarts. This lesson swaps that in-memory map for **Spring Data JPA** backed by an embedded **H2** database (a pure-Java, in-process database requiring no separate server install, the same "install-free" philosophy this repository uses throughout). Critically, the controller's public API — every endpoint, every status code — stays identical to Lesson 02; only *how* data is stored changes.

```java
@Entity
public class Task {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY) // the DATABASE assigns the id
    private Long id;
    private String title;
    private boolean done;
    // ...
}
```

`@Entity` marks a class as mapped directly to a database table; `@Id`/`@GeneratedValue` marks `id` as the primary key, auto-assigned by the database itself on insert (`IDENTITY` strategy — an auto-increment column). Note `Task` here is a plain class, not a `record` like Lesson 02's — JPA/Hibernate needs a no-args constructor and mutable fields to populate an entity via reflection when loading rows back from the database, which a record's immutable, all-args-only design doesn't support.

## Beginner: `JpaRepository` — Zero Implementation Code

```java
public interface TaskRepository extends JpaRepository<Task, Long> {
    List<Task> findByDoneFalse();
}
```

Extending `JpaRepository<Task, Long>` (the entity type and its `id` type) provides `save()`, `findById()`, `findAll()`, `deleteById()`, `existsById()`, and more — **with no implementation code written anywhere**. Spring Data generates a real, working implementation of this interface automatically at application startup.

## Intermediate: Derived Queries — SQL Generated from a Method Name

```java
List<Task> findByDoneFalse(); // Spring Data parses "findBy" + "Done" + "False" from the NAME itself
```

Verified live: calling `GET /tasks/pending` (backed by `findByDoneFalse()`) correctly returned only incomplete tasks — and after marking one task complete via `PATCH /tasks/{id}/complete`, a second call to `/tasks/pending` correctly *excluded* it. No query string was written anywhere in the code; Spring Data parsed the method name itself and generated the equivalent SQL (`SELECT * FROM task WHERE done = false`) automatically.

## Advanced: Confirming Real SQL Is Actually Executed

With `spring.jpa.show-sql=true` set, the running application's log genuinely showed Hibernate's generated SQL — verified live at startup:

```
Hibernate: create table task (id bigint generated by default as identity, done boolean not null, title varchar(255), primary key (id))
```

This confirms the persistence layer isn't just faked or mocked — a real `CREATE TABLE` statement was generated from the `@Entity` class and executed against a real (if embedded and in-memory) H2 database instance, and every `save()`/`findById()`/`findByDoneFalse()` call in this lesson's verification produced a corresponding real SQL statement underneath.

## Common Mistakes

- Using a `record` for a JPA `@Entity` — Hibernate needs a no-args constructor and mutable fields to populate an entity from a loaded database row; a record's immutable, all-args-only design doesn't support this (this is exactly why `Task` here is a plain class, unlike Lesson 02's request/response records).
- Assuming a derived query method name can be arbitrary — `findByDoneFalse()` works because Spring Data can parse `Done` (a real field on `Task`) and `False` (a supported keyword); a typo or a nonexistent field name fails at *startup*, not silently at runtime, since Spring Data validates derived query names against the entity when the application context loads.
- Relying on `ddl-auto=update` in production — it's convenient for learning and prototyping, but real production applications typically use a dedicated migration tool (Flyway or Liquibase) for controlled, versioned schema changes instead.

## Best Practices

- Keep JPA entities as plain classes with private fields and explicit getters/setters (or a well-tested Lombok setup), not records, given Hibernate's reflection-based population needs.
- Use derived query methods (`findByX`, `findByXAndY`, etc.) for simple lookups; drop to `@Query` with explicit JPQL/SQL only when a derived query name would become unwieldy or can't express the needed logic.
- Use `spring.jpa.show-sql=true` (or a proper logging framework configuration) during development to see the actual generated SQL — verifying the ORM produces the queries you expect avoids the common trap of code that "works" but issues wildly inefficient SQL.

## Real-World Usage

Spring Data JPA (backed by Hibernate) is the dominant persistence approach for production Java/Spring applications talking to relational databases (PostgreSQL, MySQL, SQL Server) — this lesson's H2-backed setup is specifically for install-free learning; a real deployment would simply change the `spring.datasource.url`/driver in `application.properties` to point at a real database server, with the entity/repository/controller code unchanged, exactly demonstrating why the JPA abstraction is valuable.

## Summary

- Spring Data JPA replaces manual data-access code with `@Entity` classes and `JpaRepository` interfaces requiring zero implementation code.
- Derived query methods generate real SQL from a method's name — verified live to correctly filter tasks by their `done` state, both before and after a state change.
- H2 provides a genuine, embedded, install-free database for learning and testing — verified live via real `CREATE TABLE` SQL in the application's own startup log.

## Key Terms

- **`@Entity`** — marks a class as mapped directly to a database table.
- **`JpaRepository<T, ID>`** — a Spring Data interface providing CRUD operations with no implementation code, for an entity type `T` with primary-key type `ID`.
- **Derived query** — a repository method whose SQL is generated automatically by parsing its method name.

## Interview Questions

1. **Why is `Task` a plain class in this lesson, when Lesson 02 used a `record` for the same conceptual data?**
   JPA/Hibernate populates an entity's fields via reflection when loading a row from the database — it needs a no-args constructor to first create an empty instance, then sets each field individually. A Java `record`'s canonical constructor requires *all* fields to be supplied at once, and its fields are immutable (final) after construction, which doesn't fit Hibernate's "construct empty, then populate" reflection-based loading process. A plain class with a protected/no-args constructor and mutable fields (as used in this lesson) is the standard, necessary shape for a JPA entity.

2. **How does a Spring Data derived query method like `findByDoneFalse()` actually work, with no query written anywhere?**
   At application startup, Spring Data parses the repository interface's method names according to a defined convention (`findBy` followed by field names and optional keywords like `And`/`Or`/`True`/`False`/`GreaterThan`, etc.), matches them against the entity's actual fields, and generates the corresponding SQL/JPQL query automatically. Verified live in this lesson: `findByDoneFalse()` correctly translated to a query selecting only tasks where `done = false`, confirmed by its result correctly excluding a task immediately after that task was marked complete via a separate `PATCH` request.
