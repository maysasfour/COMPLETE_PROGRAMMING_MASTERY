## Concept

Kotlin generics are, like Java's, erased at runtime by the JVM (Lesson 11's `is`/`as` checks against a generic type parameter don't work by default, mirroring Java's erasure exactly) — but Kotlin's *variance* system is genuinely different. Java requires **use-site variance**: every call site that needs covariance/contravariance must repeat a wildcard (`List<? extends Animal>`). Kotlin allows **declaration-site variance**: the class itself declares once, at its definition, whether its type parameter is covariant (`out T`) or contravariant (`in T`), and every use of that class then automatically gets the correct variance with no repeated wildcard syntax.

## Invariant by Default: `Box<Dog>` Is *Not* a `Box<Animal>`

```kotlin
class InvariantBox<T>(val item: T)
val dogBox: InvariantBox<Dog> = InvariantBox(Dog("Rex"))
// val animalBox: InvariantBox<Animal> = dogBox // COMPILE ERROR
```

Verified live: assigning an `InvariantBox<Dog>` to an `InvariantBox<Animal>`-typed variable produces:

```
error: initializer type mismatch: expected 'InvariantBox<Animal>', actual 'InvariantBox<Dog>'.
```

This is the safe, invariant default — the same behavior Java's plain (wildcard-free) generics have.

## Declaration-Site Variance (`out T`): The Fix, Declared Once

```kotlin
class CovariantBox<out T>(val item: T) // declared covariant ONCE, at the class definition
fun printAnimalName(box: CovariantBox<Animal>) = println(box.item.name)

val covariantDogBox = CovariantBox(Dog("Fido"))
printAnimalName(covariantDogBox) // WORKS -- CovariantBox<Dog> genuinely IS a CovariantBox<Animal>
```

Verified live: with `out T` declared on the class itself, a `CovariantBox<Dog>` was accepted directly where a `CovariantBox<Animal>` parameter was expected — no wildcard needed at the call site at all. In Java, achieving the equivalent would require writing `List<? extends Animal>` (or similar) at *every* call site needing this flexibility — Kotlin's declaration-site variance means the class author decides and encodes the variance once, and every consumer automatically benefits, a genuine ergonomic and safety improvement (since a use-site wildcard can be forgotten at some call sites and not others, while declaration-site variance is enforced everywhere uniformly).

## `reified` Type Parameters: Checking `T` at Runtime

```kotlin
inline fun <reified T> isInstance(value: Any): Boolean = value is T

isInstance<String>("hello") // true
isInstance<Int>("hello")      // false
```

Ordinary generic functions cannot perform `value is T` — the JVM erases `T` at runtime (matching Java's erasure, covered in this repository's Java course), so there's nothing left to check against. Marking a function `inline` and its type parameter `reified` tells the compiler to substitute the *actual* type argument directly into the generated bytecode at each call site (since the function's body is inlined, not compiled once and shared), making the type available for real runtime checks like `is T` — a genuine capability plain (non-inline) generics cannot provide, in Kotlin or Java.

## Common Mistakes

- Assuming Kotlin generics are covariant by default, the way arrays are in some languages — they're invariant by default, verified live; covariance requires the explicit `out` modifier.
- Trying to perform `value is T` inside an ordinary (non-`inline`, non-`reified`) generic function — this fails to compile with an erased-type error, exactly like Java's generics; only `inline fun <reified T>` makes runtime type checks against a generic parameter possible.
- Forgetting `reified` requires the enclosing function to be `inline` — the two modifiers are inseparable; `reified` cannot be used on a type parameter of a non-inline function at all.

## Best Practices

- Mark a generic class's type parameter `out` when it's only ever produced/returned (never consumed as a function parameter) — a "read-only" container — to get automatic, safe covariance for free.
- Mark a type parameter `in` when it's only ever consumed (never produced/returned) for contravariance, following the same reasoning in reverse.
- Reach for `reified` type parameters specifically when a generic function genuinely needs to inspect or construct instances of `T` at runtime (deserialization helpers, type-checking utilities) — but be mindful that `inline` functions are copied into every call site, which can increase compiled code size if overused for large function bodies.

## Real-World Usage

Kotlin's `out`/`in` declaration-site variance is used extensively throughout its own standard library (`List<out T>` is covariant, for instance, letting a `List<String>` be used directly wherever a `List<Any>` is expected) — a genuine, practical ergonomic win over Java's `List<? extends Object>`-style wildcards needing to be written explicitly at every relevant call site.

## Summary

- Kotlin generics are invariant by default, erasure-based at runtime (matching Java) — verified live via a real compile error for an invalid invariant assignment.
- `out`/`in` provide declaration-site variance, encoded once at the class definition, unlike Java's repeated use-site wildcards — verified live to make a covariant assignment succeed with no call-site annotation needed.
- `reified` type parameters (only on `inline fun`) allow genuine runtime type checks against `T`, something ordinary generics cannot do due to JVM erasure.

## Key Terms

- **Declaration-site variance** — variance (`out`/`in`) declared once on a generic class's type parameter, applying automatically everywhere that class is used.
- **`reified`** — a type parameter modifier (only valid on `inline fun`) preserving the actual type argument at each call site for runtime use.

## Interview Questions

1. **How does Kotlin's declaration-site variance (`out`/`in`) differ from Java's use-site variance (wildcards), and what practical problem does it solve?**
   In Java, a generic class's variance must be specified at each individual use site via a wildcard (`List<? extends Animal>` for covariance, `List<? super Dog>` for contravariance) — every caller needing that flexibility must remember to write the wildcard, and it's easy to omit at some call sites and not others. Kotlin instead lets the class *author* declare variance once, at the class definition (`class Box<out T>`), and every subsequent use of that class automatically respects it with no repeated annotation needed — verified directly in this lesson, where a `CovariantBox<Dog>` was accepted wherever a `CovariantBox<Animal>` was expected, with zero wildcard-like syntax at the call site. This is both more concise and more consistently safe, since the variance guarantee can't be forgotten at an individual call site.

2. **Why can't an ordinary generic function perform `value is T`, and what does `reified` change about that?**
   Because the JVM erases generic type parameters at runtime — by the time compiled bytecode executes, there's no runtime representation of `T` left to check `value` against, exactly mirroring Java's type erasure (covered in this repository's Java course). Marking a function `inline` and its type parameter `reified` changes this: since an inline function's body is copied directly into each call site at compile time (rather than compiled once and shared), the compiler can substitute the actual, concrete type argument used at that specific call site directly into the generated code, making a genuine `is T` runtime check possible — verified live in this lesson (`isInstance<String>("hello")` correctly returning `true`). This capability is unique to `inline`/`reified` functions; it's not available to ordinary generic functions in either Kotlin or Java.
