# 21 — Solutions

Runnable solutions for every problem in [20-Exercises](../20-Exercises/README.md). Each `SolutionN.java` matches Exercise N. All seven have been executed and verified — the "Verified output" blocks below are real, not predicted.

## Solution 01 — FizzBuzz Variant

```
[1, 2, Fizz, 4, Buzz, Fizz, 7, 8, Fizz, Buzz, 11, Fizz, 13, 14, FizzBuzz]
```

Check `i % 15 == 0` (both 3 and 5) **before** checking `% 3` or `% 5` individually — if `% 3` were checked first, multiples of 15 would hit the `"Fizz"` branch and never reach the combined case, since `else if` short-circuits.

## Solution 02 — Word Frequency Counter

```
{the=2, cat=2, sat=1, ran=1}
```

`replaceAll("[.,!?]", "")` strips the punctuation characters in one pass; `Map.merge(word, 1, Integer::sum)` either inserts a new key with value `1` or adds `1` to an existing value, in a single call — avoiding a manual "does this key exist yet?" check. `LinkedHashMap` (rather than plain `HashMap`) keeps the printed order matching first-seen order, purely for readability of the output; the exercise itself only requires matching key/value pairs, not a specific order.

## Solution 03 — Validated Bank Account Class

```
BankAccount(owner=Ada, balance=150.00)
Deposit of -5 rejected: Deposit amount must be positive
Withdrawal blocked: Cannot withdraw 500.0 - balance is only 150.0
BankAccount(owner=Ada, balance=100.00)
```

The real balance lives in a `private` field with no public setter — the only sanctioned way to change it from outside the class is through `deposit`/`withdraw`, both of which enforce validation. `InsufficientFundsException` is a **checked** exception (extends `Exception`, not `RuntimeException`) specifically because a caller genuinely needs to be forced to handle "insufficient funds" as a real possibility, unlike a programmer-error-style unchecked exception.

## Solution 04 — Deduplicate While Preserving Order

```
Loop version:        [3, 1, 2, 4]
LinkedHashSet version: [3, 1, 2, 4]
Both match: true
```

`LinkedHashSet` maintains insertion order natively — re-adding an already-present element is a no-op that does not move its position — so wrapping one in a `new ArrayList<>(...)` gives first-seen order "for free," without writing an explicit loop. The manual loop version demonstrates the same result achieved with a plain `HashSet` used only for its O(1) membership check, with the result list built explicitly in encounter order.

## Solution 05 — Safe Division with Custom Exceptions

```
Plain 5.0 / 0.0 (no custom check) = Infinity (Infinity, not an exception)
10 / 2 = 5.0
Custom error caught: Cannot divide 5.0 by zero
Custom error caught: Cannot divide '10' and 'abc' - invalid number format (caused by: NumberFormatException)
8 / 4 = 2.0
```

A genuinely useful thing confirmed directly rather than assumed: Java's own floating-point division by zero does **not** throw at all — it produces `Infinity` (or `NaN` for `0.0/0.0`) per IEEE 754, which is exactly why a domain that needs an actual exception for this case has to add its own explicit check. `InvalidNumberFormatException(message, cause)` passes the original `NumberFormatException` to the two-argument `Throwable` constructor, preserving it as `getCause()` — confirmed directly by printing `e.getCause().getClass().getSimpleName()`.

## Solution 06 — Generic Stack with Bounded Type

```
int stack after pushes: length 3
Popped: 3
Peeked (unchanged): 2
Size after pop: 2
string stack popped: b
string stack popped: a
Popping empty stack correctly threw: Cannot pop from an empty stack
```

The custom `Stack<T>` (deliberately shadowing `java.util.Stack`, never imported here) works identically for `Stack<Integer>` and `Stack<String>` — the same generic class, instantiated with two completely different type arguments, with full compile-time type safety (attempting `intStack.push("oops")` would be a compile error, not a runtime one). The custom `EmptyStackException` (unchecked, since an empty-stack pop is a programmer logic error, not a recoverable external condition) is verified to actually fire on a genuinely empty stack.

## Solution 07 — Mini Inventory System with JDBC/SQLite

```
After adding 3 items:
  Item[id=1, name=Widget, quantity=10]
  Item[id=2, name=Gadget, quantity=5]
  Item[id=3, name=Gizmo, quantity=0]
After updating Gizmo to 20:
  Item[id=1, name=Widget, quantity=10]
  Item[id=2, name=Gadget, quantity=5]
  Item[id=3, name=Gizmo, quantity=20]
Correctly caught: No item named 'Nonexistent' exists
```

`Item` is a Java `record` — an immutable data carrier with `id`/`name`/`quantity` and a free, correct `toString()`/`equals()`/`hashCode()` generated by the compiler, exactly matching Lesson 11's OOP coverage of records vs. classes. Every SQL statement uses a `PreparedStatement` with `?` placeholders (never string-concatenated SQL), the same SQL-injection-safe pattern from [16-Database-Access](../16-Database-Access/README.md). `updateQuantity`'s `ItemNotFoundException` is detected via `PreparedStatement.executeUpdate()`'s own return value (the number of rows actually affected) — zero rows affected means the `WHERE name = ?` clause matched nothing, the reliable way to detect a missing row from an `UPDATE` statement (an `UPDATE` never throws just because it matched zero rows).

## How to Run

Solutions 01–06 use Java's single-file source launcher, no build step:

```bash
cd 01-Languages/Java/21-Solutions
java Solution01.java
java Solution02.java
# ... etc.
```

Solution 07 needs the `sqlite-jdbc` driver JAR on the classpath, exactly as in [16-Database-Access](../16-Database-Access/README.md):

```bash
curl -L -o sqlite-jdbc.jar "https://repo1.maven.org/maven2/org/xerial/sqlite-jdbc/3.47.1.0/sqlite-jdbc-3.47.1.0.jar"
java -cp sqlite-jdbc.jar Solution07.java
```

(`sqlite-jdbc.jar` is not committed to this repository — downloaded on demand, covered by `.gitignore`, exactly like Lesson 16's own copy.)
